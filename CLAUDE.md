# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

IntelliJ plugin "My Air" (Kotlin), a small take on JetBrains Air: lists Claude Code sessions, resumes them in editor tabs, tracks their live status, and switches to wherever a session already runs, across windows and across IDE instances. Windows only in practice (Win32 calls through JNA).

## Commands

```bash
./gradlew test buildPlugin                                   # all tests + build/distributions/my-air-0.1.0.zip
./gradlew test --tests dev.myair.store.TabStoreTest          # one class
./gradlew test --tests 'dev.myair.store.TabStoreTest.a withdrawn*' # one test (names are backtick sentences)
```

Run the sandbox IDE without the `CLAUDE*` variables of the Claude Code session that launches it. Inherited `CLAUDE_CODE_CHILD_SESSION` makes every `claude` started in a sandbox tab turn transcript saving off, and `--no-daemon` keeps a running Gradle daemon from passing them on:

```bash
env $(env | grep -o '^CLAUDE[A-Z_]*' | sed 's/^/-u /') ./gradlew --no-daemon runIde
```

Sandbox log: `.intellijPlatform/sandbox/my-air/IU-2026.3/log_runIde/idea.log` (appended across runs). Restart the sandbox after `buildPlugin`; it does not pick up a new build by itself.

Tools › Install My Air Build and Restart (`InstallMyAirBuildAction`, shown only in a project with `build/distributions/my-air-*.zip`) installs that zip over the running My Air (`PluginInstaller.installAfterRestart`: the platform's startup script swaps the folder) and restarts the IDE without the platform's own question; it ends every `claude` running in its tabs, so it asks first when one of them works (`ExitConfirmation`).

## Build setup

- Compiles against the locally installed IDE (`local("E:/dev/apps/jetbrains/IntelliJ IDEA Ultimate")`, IU-263.7307.200; `sinceBuild` 263), not a downloaded one. Its classes are Java 25 (class version 69), hence `jvmToolchain(25)` with the IDE's own JBR registered in `gradle.properties`.
- Tests are plain JUnit 5 without the IntelliJ test framework. IDE jars are on the test classpath, so tests may use libraries the IDE ships (Gson, JNA), but not platform services. Keep logic that needs tests out of IDE-service code, as `retarget` (`TabRetargeting.kt`) and `TabStore` are.
- `ClaudeHomeWatcherTest` and `TabStoreTest` measure real file-system events and timings.
- `air-plugin/` is the unpacked JetBrains Air plugin (gitignored), kept as a reference only: inspect it with `javap`, never put it on the classpath. `docs/air-plugin-analysis.md` says how to decompile and search it and what its session tabs do; add what a new analysis finds there.

## Where the data comes from

All state is read from files `claude` writes; the plugin never talks to a `claude` process.

- **Transcripts** `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl` (`ClaudeSessionScanner`). The directory name encodes the cwd lossily, so the cwd comes from the first line carrying a `cwd` field. `claude --resume` from another folder (as after `EnterWorktree`) copies the transcript into that folder's project directory, so one session may lie in several files: the copy with the latest message, else the longest, counts. `/bg` continues a session under a new id and leaves the old transcript a `continued-in` line naming it (`continuedInSessionId`); the old session is left out while the new one is among the scanned (`ClaudeSession.continuedIn`). Title: the last `custom-title` line (`/rename`), else the brief's `title`, else the last `ai-title` line, else the first human prompt; a skill the human ran counts as `/name args` (a line opening with `<command-message>`), a built-in command such as `/model` does not. Date: the `timestamp` of the last `user`/`assistant` line or `system` `local_command` line, outside sidechains and `isMeta`; not the file's mtime, which a mere `--resume` bumps by appending `attachment`, `mode`, `last-prompt` and similar lines. Project: on every refresh a session whose cwd is in a linked worktree that `.git/worktrees/*/gitdir` of a directory sessions ran in lists gets that main checkout as `ClaudeSession.project` (`inProjects`), so the folder bound to the project holds it wherever the worktree lies; once git forgets a removed worktree, its sessions keep their own cwd. A session Claude Desktop runs gets the folder it was started in (`originCwd` of `%LOCALAPPDATA%/Claude-Data/*/claude-code-sessions/*/*/local_*.json`, keyed by `cliSessionId`, `DesktopSessionReader`), so a removed Desktop worktree keeps its sessions in the project too; such a session is marked "Desktop" in its row. Added directories: `additionalWorkingDirectories` of the last `attachment` line of type `environment` (`--add-dir`, Desktop's extra folders), shown under the session in the tree. Where it works now (`workDir`): that line's `workingDirectory`, which follows `cd` and `EnterWorktree` while `cwd` stays where it started; the branch it started on (`startBranch`): `gitBranch` of the line the cwd came from, `HEAD` (no branch, or no repository) read as none. Model and effort: `message.model` and the top-level `effort` of the last `assistant` line outside sidechains, skipping `claude`'s own error replies (model `<synthetic>`). Changed files: `Write`/`Edit`/`MultiEdit`/`NotebookEdit` `tool_use` items inside `"type":"assistant"` lines; `api-request-shape` lines also name those tools and must not count. Artifacts: the `toolUseResult` of an Artifact publish (`artifact_id`, `url`, `title`, `path`) outside sidechains, one per id, the latest publish naming it. Skills: `names` of the `attachment` lines of type `skill_listing`, the one with `isInitial` replacing the list, later ones adding to it. MCP servers: the `mcp__<server>__<tool>` names of `deferred_tools_delta` attachments, `addedNames` added and `removedNames` removed as servers connect and go; a server whose tools are only `authenticate`/`complete_authentication` waits for a sign-in and is left out. Background tasks: a `Bash`/`PowerShell` result with `backgroundTaskId` (named by the call's `description`, else its command's first line), a `Monitor` result's `taskId`, an `Agent`/`Workflow` result with status `async_launched` (`agentId` and `description`, `taskId` and `summary`); what it runs: a shell's or monitor's `command`, an agent's `prompt`, a workflow's `scriptPath` (each required); its start is that result's `timestamp`, its output file the `Output is being written to:` path of a shell's result text or an agent's `outputFile`. One ends with a `queue-operation` `enqueue` line whose `<task-notification>` carries its `<task-id>`, a `<status>` (`completed`/`failed`/`killed`/`stopped`, any other throws; a monitor's events carry none), a `<summary>` naming a command's exit code and usually `<output-file>`; an agent sent another message notifies again, and the latest end counts. An agent's model is its launch result's `resolvedModel`; an agent's or workflow's `<usage>` (after its `<result>`, whose text may hold anything) gives tokens and tool uses, a workflow's also `agent_count`/`agents_done`/`agents_error`. A monitor's notifications without a status each count as an event (its final one may carry the last); an event opening with `[Monitor expired` ends it as expired. Tasks also die with their process, which the transcript does not record. Transcripts are append-only, so a rescan reads only complete lines after the stored offset; that state is saved in `~/.my-air/scan-cache-<hash of the plugin jar's path>.json` (by the first scan, then at most once a minute and on exit; `Saved.forJar`), one per jar, so the installed plugin and a sandbox keep their own, and tagged with a hash of the jar's `dev/myair/claude/` classes, so a restart reads only what was appended meanwhile unless the transcript-reading code changed, which reads everything; `subagents/` one level deeper is not listed.
- **Live registry** `~/.claude/sessions/<pid>.json` (`LiveSessionRegistry`), one per running `claude`: `sessionId`, `status` (`busy`/`shell`/`waiting`/`idle`; `shell` counts as working, as in claude's own list), `waitingFor`, `entrypoint`, `procStart`, `cwd`, `startedAt` (each required). A running session with no transcript yet (`claude` writes one with the first message) shows in the tree and the pinned list as "New session" in that `cwd`, dated by `startedAt` (`unscannedSessions`, `ClaudeSessionsService.listed`; given its project with the scanned ones by `inProjects`), so a session started from a folder shows there at once; `sessions`, and so MCP and Session Context, keep only the scanned ones. A file outlives a killed process, so an entry counts only if the pid's start time equals `procStart`, a Windows FILETIME. `/clear` and `/resume` keep the pid and rewrite `sessionId`, which is how tabs follow their session. A file without `statusUpdatedAt` belongs to a `claude` still starting and is skipped. `kind` is `interactive` or `bg` (a background job's worker, `claude --bg` or `/bg`, which needs a `jobId`: `LiveSession.job`); `daemon` and `daemon-worker` run no session and are skipped, as is a `spare` worker started ahead for the next job, and any other kind throws. `/bg` typed in a session parks its process: its file keeps the old `sessionId` and gains `parkedJobId`, so it is no entry but goes into `parkedBy` of the job's (dropped when that job has none); when a job's worker and another process run one session, the worker is the entry.
- **Tab store** `~/.my-air/` (`TabStore`), owned by this plugin: `ides/<pid>.json` lists each IDE's session tabs, `requests/<pid>/` receives "focus this session" requests, `pins.json` holds the sessions pinned by hand, the running ones removed from the list and the settled ones (`Pins`; the list above the tree adds every session with a live process, `pinnedSessions`). Settled sessions are hidden from the list and the tree until the toolbar's Show All Sessions is on (`Pins.shown`); settling unpins, pinning unsettles. View Options can also hide from the tree (not the list) sessions whose last message is 3, 7, 14 or 30 days old. The toolbar's This Work Tree (kept per project, `dev.myair.thisWorkTree`) narrows the tree (not the list) to the sessions whose `workDir` or `cwd` lies in the work tree of the window's project, compared by root (`inWorkTree`, over `ClaudeSessionsService.heads`, which reads every session's cwd, work dir and project on each refresh), disabled outside a repository; the narrowed tree keeps its own `TreeState` (`.workTree` after the mode). Search (and `my_air_sessions_find`'s `query`) matches each word in the title, the cwd, `startBranch` or the branch checked out in `workDir` (`ClaudeSession.matches`, `branchOf`). The rows the user expanded are kept, one `TreeState` per mode (application properties `dev.myair.treeState.projects`/`.folders`, `TreeStates.kt`), across rebuilds and restarts; a search expands everything and leaves them as they were. A removed running session returns once it has a newer message and no longer works; refresh prunes dismissals that are over. Writes go to a temp file and are moved into place.

Unknown registry statuses and missing fields throw rather than being skipped; a new `claude` release that changes these formats should fail loudly.

## How the pieces fit

Packages under `dev.myair`, by feature: `claude` (reading `claude`'s files: `ClaudeSession`, scanner, registry, watcher), `store` (files in `~/.my-air` and `writeAtomically`), `folders` (folder model, `structure.json` store and history, MCP change lists), `mcp` (the toolset and its queries and JSON), `service` (`ClaudeSessionsService`, the taskbar board, tab re-targeting), `editor` (session tabs and `ClaudeSessionOpener`), `tabs` (finding tabs and windows, cross-IDE sync), `actions` (menu actions, worktrees, `Git`), `toolwindow` (the Claude Sessions panel), `prompt` (the new-session panel of the empty editor area). Tests sit in the package of what they test. Classes named in `plugin.xml` and `my-air-mcp.xml` are found at runtime only, so a move must update them.

- `ClaudeHomeWatcher` watches `sessions/` and every `projects/<dir>/`, debounced 500 ms quiet / 700 ms cap (Air's timings). `ClaudeSessionsService` (application service) refreshes on its events plus every 60 s, holds the session list and live statuses for all projects, and after each change re-targets open tabs by pid (`retarget`) and notifies subscribed tool-window panels.
- `ClaudeSessionVirtualFile` + `ClaudeSessionEditor` show a view of a reworked terminal that `SessionTerminals` (an application service) runs apart from the tab (`TransferableTerminalSessionFactory`, internal API, as Air 263's session tabs; the Ghostty VT emulator; `plugin.xml` depends on the content module `intellij.terminal.frontend`) running `claude --resume <id>` (or `--session-id <new uuid>`, in a pinned tab) with `CLAUDE_CODE_NO_FLICKER=1` and `CLAUDE_CODE_IDE_SKIP_AUTO_INSTALL=true`, and on every start, `--resume` included (claude rebuilds a recorded system prompt from the current flags after a compaction), `--append-system-prompt` with `appendedSystemPrompt` (`SessionSystemPrompt.kt`): the branch's base is `branch.<branch>.myAirBase`, read from git rather than named, so every session shares one prompt; the My Air MCP tools and what each is for (`SessionSystemPromptTest` checks it names every tool of `FoldersMcpToolset`); the plan rules (read the plan with `my_air_plan_get` at the start, keep the task's status and next step current, delete or move only with the user's agreement); and with briefs on, call `my_air_set_brief`, naming the plan task in `plan_task`; with Agents file and title their sessions on too (`MyAirSettings.fileSessions`, effective only with briefs), give it `title` and `folder` without asking, reading `my_air_folders_get` first. With briefs on it also gets `--settings ~/.my-air/hooks/brief-reminder.json` (`BriefReminder.kt`): a `UserPromptSubmit` hook, PowerShell passed as `-EncodedCommand`, that adds a reminder to every prompt until the transcript holds a `my_air_set_brief` `tool_use` (the prompt alone got it called in about a quarter of sessions). A session in a plan (`sessionPlan`: the task its brief names, else the plan row a new session was started from, `PlanStart`, else the plan folder it shows in) also gets `--append-system-prompt-file` with `planPrompt`: the plan's name, path and description, its task's and milestone's, Markdown kept whole, no statuses; the file (`~/.my-air/prompts/<IDE pid>-<uuid>.md`, `PromptFiles`) lives until the process ends, since claude reads it again after a compaction, and files of IDEs gone are deleted when the next is written. claude keeps a session's recorded prompt on `--resume` until a compaction, so a session resumed into a plan gets the context only then. A session a background job runs (the registry read afresh at start, as a restored tab may start before the first refresh) gets `claude attach <jobId>` instead, with the same variables and nothing else, since claude refuses or forks a `--resume` of it; the tab keeps the job (`ClaudeSessionVirtualFile.job`) and follows the job's entry rather than its pid, as a tab parked by `/bg` follows the job it parked into (`shownBy`, used by `retarget` and the statuses `SessionTerminals` reads). `SessionTerminals` learns the process pid from `TransferableTerminalSession.processId` (`claude` itself, not a shell); text typed for it goes through the view's `sendText`. One process per tab file: a tab binds a view of it (`attach`, `bind`), a second tab of the same file (a split) takes it and the first shows Show Here. Closing the tab (`release`) ends the process unless Keep sessions running after their tab closes is on (`MyAirSettings.keepDetached`, default) or the platform closes it to reopen it (`CLOSING_TO_REOPEN`); then it runs on detached, and every refresh ends a detached one that `retires` (`Retirement.kt`, as Air's `DetachedTerminalRetirement`: detached at least 60 s, `idle`, no background task started by this process still open; needing input keeps it); closing a working session's tab says so once per run. A process showing a job (`jobOf`: attached, or parked into one) is only a view of it: closing its tab ends it unless the tab reopens, whatever the setting, and the job runs on. A detached session counts as a tab wherever one does (`SessionHosts.findTab`/`openTabs`, `retargetOpenTabs`, the heads), so opening it from anywhere reopens the same file and binds the same process. Close and Settle, a process ending by itself and closing its project (`SessionTerminals.ProjectClose`) end it. Closing a project, exiting or restarting the IDE first asks when a process it would end `interrupts` (`CloseConfirmation.kt`, as Air's `AgentThreadViewProjectCloseHandler`: the registry says working or needing input, or a background task it started runs; idle, starting and ended ones never, nor a view of a job): `ProjectCloseConfirmation` (`projectCloseHandler`) about the processes that last showed in that project, tab or detached, and not during an exit; `ExitConfirmation`, an `ApplicationListener` that `SessionTerminals` registers when it is created, about all of them. The texts come from `confirmation`; the statuses from the last refresh. The tab's icon is the session's status, with a branch badge in its corner when the session works in another work tree than its home (`TabMark`, `tabMark`: the window's work tree for a session of the window's project, its project's otherwise; compared by root, from `workDir`, so `EnterWorktree` counts; the heads are read from HEAD files on the refresh thread, `Git.head`, kept in the service state so a checkout alone re-marks, and the mark stored on the tab by `retargetOpenTabs`, so the providers do no IO); a session of another project than the window's gets that project's icon after it and its colour, a session of the window's project in another work tree that tree's colour, either mixed into the tab background (`ClaudeSessionTabColorProvider`, `projectColor`: the internal `ProjectIconPalette`, as the initials icon picks it, which asserts the EDT while tab colours are asked for off it, so it is read there once per path and the tab repainted); the tooltip names the project, and for a worktree its root and branch (`tabTooltip`). Close and Settle (`CloseAndSettleAction`, in `CloseEditorsGroup` after Close, so in the tab's menu) settles the tab's session, then closes it; when the tab shows a job the registry still lists it also runs `claude stop <jobId>` off the EDT (5 s, as Air's Mark Done; a timeout or a non-zero exit is logged as an error with its stderr). Tabs survive a restart: the file's URL is `myair-session://<id>?cwd=…&project=…` in `ClaudeSessionFileSystem` (`SessionTabUrl.kt`), computed from the session it shows now, so the platform saves it with the open tabs (order, splits, pins) and resolves it on startup, always as a new tab and never into Recent Files (`OptionallyIncluded`); a restored tab gets `--resume`, or `--session-id` when the session has no transcript yet, and starts when first selected, but not while its directory is gone or the registry shows its session running other than as a job, where it says so and offers Switch to Window / Open Anyway. `CenteredTerminal` gives the terminal the number of columns set as Session tab width (`MyAirSettings.terminalColumns`, 0: the whole tab) and centers it, counting columns as the terminal's editor does (visible width over `CharacterGrid.charWidth`, rounded down; `EditorGrid` reads the visible one of the output and alternate-buffer editors); `CenteredTerminalTest` lays out a scroll pane in a border standing for that editor.
- `ClaudeSessionOpener.open` goes, in order: a tab in this IDE (`SessionHosts.findTab`, which includes Air's tabs read through reflection on `getThreadId`/`getSessionId`) → a tab in another IDE running this plugin (`TabsSync.focusElsewhere`: `AllowSetForegroundWindow` for that IDE, then a request file) → a warning when the registry shows the session running in another program other than as a background job (which a new tab attaches to), offering its window (`SessionHosts.hostWindow`, the nearest ancestor of the `claude` process that owns a visible window) → a new tab. An agent starts a new session with the MCP tool `my_air_session_start` (`FoldersMcpToolset`): a configuration by name and/or model, effort, directory, added directories, a worktree off a base it must name, maybe on a new branch (`createWorktree`, the popup-free core of `startInWorktree`), a plan task (`PlanStart`), and a folder, which files the session and, without a directory, gives it as the tree's menu does; the tab opens in the IDE project the call came through, and every input or `git` failure (`GitFailure`) goes back to the agent instead of a dialog (`sessionStartPreset`, `SessionStart.kt`).
- `NewClaudeSessionInWorktreeAction` (toolbar and Tools menu, next to the plain new-session action) lists branches in a popup: the default branch (`origin/HEAD`; without `origin` the one local `main`/`master`), the 5 recent bases (application `PropertiesComponent`, keyed by the repository's main checkout), the rest. The pick's local branch (a remote pick: its local namesake, created tracking it when missing) is checked out in `<worktrees dir>/<name>` without a new branch (`Git.addWorktree`); a linked worktree holding it is removed first (`git worktree remove`) when it is clean (no modified or untracked file), unlocked and no running session works in it. When it cannot be, or the main checkout holds it, the pick becomes the base of a new branch `worktree-<name>` (`git worktree add --no-track`, `addBranchWorktree`), the pick stored as the branch's base in the repository's config (`branch.<branch>.myAirBase`, `Git.setBase`, so `git branch -m` carries it), `<name>` being `worktreeName`: the pick without non-alphanumerics, today's date and the first 4 characters of the new session id (`main-2026-10-28-3fb8`); gitignored files matching `.worktreeinclude` are copied in, as `claude --worktree` does (`claude` itself takes no base branch). After the base, the action (and the tree menu's) offers Check out <base> or New branch off <base>... (`branchPopup`): a popup in the composer's look (`showNewBranchPopup`, `NewBranchPanel.kt`; the card, bar, chips and send button are shared in `Composer.kt`) takes a flat name typed or suggested from a task or a Jira key (`suggestBranchName`, `BranchNames.kt`: `claude -p --model haiku --no-session-persistence`, so it leaves no transcript, with `--allowedTools` the Jira tools set in Settings (`MyAirSettings.jiraTools`); Haiku answers with a slug alone and the first Jira key of the task (`ticketKey`) goes before it, `TR-1234-short-description`); `addBranchWorktree` makes it off the base in `<worktrees dir>/<branch>` (`dirName`), the base stored. The worktrees dir is an application setting (`MyAirSettings`, the one class left in `dev.myair`, Settings › Tools › My Air), default `.claude/worktrees`, relative to the main checkout. `Git` (`Git.kt`) runs the `git` on PATH and throws with its stderr; the pure parts (`baseChoices`, `pushRecent`, `defaultBranch`, `worktreePath`) are in `Worktrees.kt`, and `GitTest` runs real `git` in a temp dir. The tree's menu on a project row, or on a folder that has or lies in one with a working directory or a bound one, offers both new-session actions in that directory (`nodeDir`, `NewSessionInDirAction`): the nearest such folder decides, its `workdir` before its first bound directory (`startFolder`, `Folder.startDir`), and one gone disables them rather than handing over to a folder above; a session started from a folder row is filed in that folder (`startNew`'s `folderId`). Open in IDEA and Open in Terminal (`OpenInDir.kt`) sit beside them, on session rows too (`openDir`: the session's cwd) and as IDEA and Terminal links at the end of the project row in the context pane's Environment section: IDEA focuses the open project of this IDE or opens it here, Terminal adds a tab at the directory to this project's Terminal tool window.
- Session configurations (`Preset`, `store/Presets.kt`) live in `~/.my-air/presets.json`, shared by every IDE and edited in Settings › Tools › My Air (`PresetsEditor`, `PresetDialog`; the fixed base is picked from the branches read off the EDT from the project field's repository, or the IDE project's when it is empty): name, `--model`, `--effort`, a project directory (none: the IDE project's), no worktree / a worktree off a fixed base / off a base picked in the popup (`startInWorktree`), `--add-dir` directories, and whether it gets its own toolbar button (an initials icon). `PresetsGroup` on the panel toolbar shows those buttons and a dropdown of all presets; it reads the file on every toolbar update, cached by modification time, and names a broken file in the dropdown. A session's menu (tree and list) offers New Session with Same Settings and Save Settings as Configuration...; both take `presetOf(session)`: its model, effort, project, added directories, and a worktree with the base picked at start when its cwd is not its project.
- `PromptPanel` (`prompt/`), styled after Air's composer: a card with the first message, chips for the configuration (Default, then `presets.json`), model (default `opus`) and effort (default `medium`) and a send button; under it a bar with the workspace (current checkout, a new worktree, or a new worktree on a new branch, named in a field beside it or by its Suggest from the message, as that popup does) and the branch, the checked-out one or, for a worktree, the base picked in a searchable list (`baseChoices` of the configuration's directory's repository, read off the EDT, tagged current/default/recent by `branchTag`). A configuration sets the rest, each may then be changed, and the next panel opens on the last start's choices (`restore`, `PromptChoices.kt`; the base through the recent bases), or on a message typed and not sent with the choices and base it was typed with (`Draft`, `opening`; application properties `dev.myair.prompt.draft.*`, written on every change while there is a message, removed when it is sent or emptied). Ctrl+V of an image saves it as a PNG in `~/.my-air/images/` (images older than 30 days are deleted, off the EDT, whenever a panel opens: `pruneImages`) and of copied files keeps them where they are; either goes into the message as an `@path` mention, quoted when it has a space (`pastedMentions`, `PastedImages.kt`), which `claude` attaches at once, while a bare path it reads only with a tool call. The paste is an action on the text area, since the IDE's own paste takes only text. It starts the session through `startPreset`. The prompt goes last, after `--` (`Preset.claudeArgs(prompt)`): `--add-dir` is variadic and a lone word like `mcp` would be a subcommand. It fills the empty editor area (`PromptEmptyState`, platform EP `editorEmptyStateComponentProvider`, internal API in `fileEditor.impl`); every available `RICH` provider is stacked there, so Air's composer shows too unless its registry key `air.inline.empty.state.prompt` is off. `NewSessionWithPromptAction` (first on the main toolbar and the Claude Sessions toolbar, and in the Tools menu) shows the same panel in a popup.
- `taskbar/` is a separate WPF app (.NET 10, `Deskband11Lib.Wpf`) that hosts a window inside the Windows 11 taskbar: counts of sessions needing input, with an unread reply, and working; hover peeks at a flyout listing them in those groups, a click pins it. When a session comes to need input or gets an unread reply (`Board.Arrivals`, between two reads of the board, never on the first read nor without a live IDE), a bubble above the widget (`Bubble`) names it; it hides after 8 s unless hovered, drops a session that leaves that group, gives way to the flyout, and a click opens the session as a flyout row does. The bubble activates itself before asking the IDE: a click alone does not make a non-activated window the foreground, and without it the IDE cannot come forward. Every IDE writes `~/.my-air/taskbar/board.json` when a refresh changes it (`boardSessions`/`boardJson` in `TaskbarBoard.kt`, written by `BoardWriter`); the app reads it and `ides/*.json`, and a click on a row sends a focus request to the IDE with the session's tab, else any IDE, whose `TabsSync` then opens the session. Unread: an idle session whose last message is newer than `~/.my-air/seen/<id>` (epoch ms, one file per session, `Seen.kt`); the IDE marks a session seen when its tab is selected in the active window (`SessionHosts.visibleSessions`, on tab selection, IDE activation and refresh), the app when a row is clicked, and a session met for the first time is marked at its last message. The same unread sessions (`ClaudeSessionsService.unread`) get a bold title in the tree and the pinned list and the blue asterisk there and on their tab. `TaskbarBoardTest` and `taskbar/tests/BoardTest.cs` parse the same JSON literal. Build/test: `pwsh taskbar/build.ps1` stops a running `MyAirTaskbar` (it locks its exe, which the tests' Debug build also writes), runs `dotnet test taskbar/tests`, runs `dotnet build -c Release taskbar` and starts the new build.
