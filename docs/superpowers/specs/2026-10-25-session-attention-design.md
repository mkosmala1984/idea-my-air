# Session briefs and "next session that needs me"

## TL;DR

- **Goal:** see what each session is for (a one-sentence goal and its task list with progress) without opening it, and reach the sessions waiting for the user with one shortcut.
- **Brief written by the agent (user's decision):** a new MCP tool `my_air_set_brief(goal, tasks)`. The tool itself stores nothing: the call and its arguments land in the calling session's transcript, and the scanner reads the latest one, the way it reads edited files. So the brief belongs to the right session without the tool knowing which session called it. Claude Desktop sessions' `mcp__ccd_turn__update_plan` calls give tasks in the same format.
- **Where it shows:** the row gets `2/5 · <task in progress>`; the session's children in the tree start with the goal and the tasks (✓ ▶ ○), above the changed files; the tooltip shows the whole brief; the taskbar flyout's second line shows the task in progress.
- **Shortcut:** "Next Session Needing Me": needs-input sessions (longest waiting first), then unread replies (oldest first), all projects and IDEs; again → the next one, wrapping. A session without a tab: its window comes to the front; no window → the existing "Session Already Running" dialog (user's decision).
- **Switch:** Settings › Tools › My Air › "Session briefs" (on by default). Off: no brief is shown anywhere (rows, tree, tooltip, flyout) at once; the tool leaves the MCP server after an IDE restart (the server lists tools at startup only).
- **Instruction (user's decision, done):** added to the global `~/.claude/CLAUDE.md` once the implementation was committed; it applies "when the tool is available", so it is inert until the plugin is installed and the IDE restarted.
- **No TodoWrite:** none of the last 300 local transcripts has a `TodoWrite` call (CLI 2.1.310), so it is not a source.
- **Risks:** `board.json` is parsed strictly by the taskbar app, so the plugin, `Board.cs` and both board tests change in one commit. The tool exists only while an IDE with the plugin runs.
- **Out of scope:** model-generated summaries, a global hotkey in the taskbar app, `/goal` state, PR/CI status.

## Why

The article that prompted this (thebuildingmachine.com, "My new agentic workflow") names the failure: with many agents running, the author lost track of which agent owned what and kept asking them to remind him. My Air shows status (working / needs input / unread reply) and a title, but not the goal or how far along the work is; to learn it the user opens the tab and scrolls. The user asked for the goal and a short list of points or tasks rather than the current tool call.

## Goals

- Each session that has a brief shows its goal and task list, with progress, in the tree, the tooltip and the flyout.
- The agent keeps the brief current by calling one tool with the whole brief.
- One keystroke takes the user to the next session waiting for them; repeated keystrokes walk through all of them.

## Non-goals

- Briefs for sessions whose agent never calls the tool: they show what they show today, and the tooltip their first prompt.
- Summaries generated by a model.
- History of briefs; only the latest call counts.

## Anti-goals

- Slowing the first scan noticeably: the scanner must not JSON-parse every assistant line.
- Accepting malformed briefs silently: the tool rejects bad input with an error the agent sees; the scanner throws on a recorded call it cannot read, like the rest of the scanner.

## Behaviour

### The tool

In a toolset of its own, `BriefMcpToolset`, registered in `my-air-mcp.xml` next to `FoldersMcpToolset`, so the switch below can turn it off on its own through `McpToolset.isEnabled()` (an interface method of the IDE's MCP server, checked with `javap` on `mcpserver.jar`):

`my_air_set_brief(goal: String, tasks: String)`
- `goal`: one sentence, 1–200 chars, what the session is for.
- `tasks`: JSON array (a string, as `my_air_folders_apply` takes its changes) of `{"content": "...", "status": "pending" | "in_progress" | "completed"}`, 0–15 items, each `content` 1–120 chars, at most one `in_progress`. The same item format as `update_plan`.
- Replaces the whole brief on every call. Returns `ok`. Invalid input → an error naming the rule broken; the call then still sits in the transcript, so the scanner ignores calls whose result is an error *(see below)*.
- Description (the agent reads it): call it after the first user request is understood, and again whenever the goal changes or a task starts or finishes; keep tasks as outcomes, not tool steps; write in the user's language.

### The switch

`MyAirSettings.Options` gains `briefs` (boolean, default `true`), shown in `MyAirConfigurable` as a checkbox "Session briefs: let agents describe their goal and tasks (my_air_set_brief) and show them", under the worktrees row.

- `BriefMcpToolset.isEnabled()` returns the setting. The MCP server reads it only when it builds its tool list: `McpToolsListProvider.emitMcpTools` runs at startup and on extension-point changes (checked with `javap` on `mcpserver.jar`, IU-262.10968.63). So the tool follows the setting after an IDE restart; the checkbox comment says so.
- Off, the UI shows no brief: no `2/5 · ...` in the label, no goal and task rows in the tree, no brief in the tooltip (the first prompt stays), no `activity` in `board.json` from briefs. The scanner keeps reading briefs either way *(my call: one code path; turning the setting on again shows them at once)*.
- Changing the setting calls the panels' refresh, so the tree redraws without waiting for the next file event.

### Reading it

- The scanner remembers the raw text of the last main-conversation assistant line holding a `tool_use` whose `name` ends with `__my_air_set_brief`, or equals `mcp__ccd_turn__update_plan`, and parses it after the read loop (cheap substring check first, as `EDIT_TOOL_USE` does). The server prefix (`mcp__idea__`) comes from the user's MCP config, hence the suffix match.
- A call whose `tool_result` (matched by `tool_use_id`) has `is_error: true` does not count *(my call)*. Calls made in one message are all written before their results, so the scanner keeps pending calls by id and applies each when its accepted result arrives (found live: an accepted call followed by a rejected one was lost).
- `update_plan` gives tasks only, in three forms found in the local transcripts: `{"items": [...]}` sets the plan; `{"advance": true}` completes the step in progress and starts the next pending one; `{"done": [1, 2], "start": 3}` completes and starts steps numbered from 1 (its result reads "Plan updated: step 3 of 5 is in progress"). A later `my_air_set_brief` replaces it and vice versa.
- `ClaudeSession` gains `brief: Brief?` (`goal: String?`, `tasks: List<BriefTask>`), carried in `Transcript` across incremental reads. Its equality already changes with every assistant line through `lastMessage`, so the refresh rate does not change.

### Tree and pinned list

| Element | Without a brief | With a brief |
|---|---|---|
| Row label | as today | `2/5 · <in-progress task>` before the status label; `2/5` alone with no task in progress; nothing with no tasks |
| Session's children (tree) | changed files | goal row (bulb icon), then one row per task (✓ completed greyed, ▶ in progress bold, ○ pending), then changed files |
| Tooltip | `Asked: <first prompt>` (first line, 200 chars) | goal, then the tasks as in the tree, then `Asked: ...` |

A needs-input row's tooltip starts with `Waiting for: <waitingFor>`. Brief rows are not draggable or openable; double-click opens the session, as on the session row *(my call)*.

### Taskbar flyout

`BoardSession` gets `activity` (string, may be absent): the in-progress task, else the goal. `Board.Detail` becomes `<project> · <activity>` (unread rows keep `finished N min ago` before it), with the full line as the row's tooltip. `Board.cs`, `TaskbarBoardTest` and `taskbar/tests/BoardTest.cs` (the shared JSON literal) change with `TaskbarBoard.kt`.

### Instruction for sessions (added to `~/.claude/CLAUDE.md` as the last step, once the tool works)

```
# My Air brief
When the my_air_set_brief tool is available, call it once you understand the user's first request:
a one-sentence goal and up to 15 tasks with status. Call it again whenever the goal changes or a task
starts or finishes.
```

### Action "Next Session Needing Me"

- Registered in `plugin.xml` next to "Focus Claude Session...", in the Tools menu, with the default shortcut Alt+Shift+K in `$default`: free in the installed IDE's default keymap, its bundled plugins and the user's "Windows copy" keymap (Alt+Shift+N there is `tasks.goto`).
- **Queue**, computed when the action runs: (1) needs-input sessions, oldest `statusUpdatedAt` first (`LiveSession` gains `since: Instant` from that field); (2) unread sessions (`ClaudeSessionsService.unread`), oldest `lastMessage` first. Settled sessions are included *(my call)*.
- **Which one:** the current session is the one in the selected tab of the active window when it is in the queue, else the one this action last went to (kept in memory per IDE, *my call*, so a walk through sessions in terminals or Claude Desktop does not restart). The pick is the next after the current one, wrapping; with no current one in the queue, the first. A one-element queue already shown → the hint below.
- **Going there:** `ClaudeSessionOpener.open`, except for a session running outside every IDE tab: then its `SessionHosts.hostWindow` comes to the front without the dialog; no window (including `claude` in this IDE outside an editor tab) → `open` as today, which shows "Session Already Running" *(user's decision)*.
- **Empty queue:** a balloon over the active window: "Nothing needs you · 3 working".
- An unread session opened this way is marked seen by the existing tab-selection path and leaves the queue; a needs-input one stays until its status changes.

## Tests

- `ClaudeSessionScannerTest`: brief from `my_air_set_brief` and from `update_plan`; the later one wins; a call with an error result is ignored; sidechain calls ignored; brief kept across an incremental read with no new call; malformed recorded call throws.
- Tool input validation as a pure function, unit-tested (each rule).
- Queue order and the next-after-current pick as a pure function next to `boardSessions` (both groups, wrap, current not in queue, remembered last pick, empty).
- `LiveSessionRegistryTest`: `since` from `statusUpdatedAt`.
- Board JSON literal updated in both test suites.
