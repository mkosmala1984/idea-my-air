# Plan View Implementation Plan

## TL;DR

- **Goal:** a plan folder opens in an editor tab. The left side edits the description, milestones and tasks in place and shows each task's sessions and actions. The right side embeds the plan's manager Claude session.
- **Approach:** 8 tasks.
  1. A store for managers.
  2. Extract the terminal part of `ClaudeSessionEditor` into `SessionPane`, which both editors use.
  3. Add the plan files registry, file system and manager start.
  4. Teach session-tab lookups about plan tabs.
  5. A tested view model.
  6. The editor UI.
  7. Opening.
  8. Docs and a sandbox check.
- **Deviation from the spec (my call):** the manager instructions go into the plan prompt file (`planPrompt(..., manager = true)`), not into a second `--append-system-prompt`. This is one mechanism, already re-read after compaction.
- **Risk:** Task 4 touches every place that finds session tabs. Only a sandbox run proves it, against the behaviour table of the spec.
- **Out of scope:** as in the spec (dragging, several managers, editing the folder itself).

**Goal:** A plan folder opens in an editor tab with the plan editable in place and its manager Claude session embedded beside it.

**Architecture:** `PlanEditor` (on `PlanVirtualFile`, `myair-plan://<folderId>`) holds an `OnePixelSplitter`: `PlanPanel` on the left, rebuilt from `ClaudeSessionsService` on every change, and a `SessionPane` on the right. The `SessionPane` shows the manager's `ClaudeSessionVirtualFile`, which `SessionTerminals` runs like any session. `PlanFiles`, an application service, owns one `PlanVirtualFile` per plan and its manager file, so a reopened tab binds the same process.

**Tech Stack:** Kotlin, IntelliJ Platform 263 (Kotlin UI DSL, `FileEditor`, `DeprecatedVirtualFileSystem`, reworked terminal through `SessionTerminals`), Gson, JUnit 5.

**Spec:** `docs/superpowers/specs/2026-11-08-plan-view-design.md`

## Global Constraints

- English in code, comments, strings and test names. Test names are backtick sentences, as in the rest of `src/test`.
- No fallbacks: unknown keys and malformed JSON in `plan-managers.json` throw, like `Pins.parse`.
- Every folder edit goes through `ClaudeSessionsService.updateFolders(ChangeSource.UI, …)`.
- `~/.my-air/plan-managers.json` is written with `writeAtomically`.
- The run command is `./gradlew test buildPlugin` (Gradle wrapper, from the worktree root).
- Every commit ends its trailer block with `Plan-Task: N/8` and `Plan: docs/superpowers/plans/2026-11-08-plan-view.md`.
- Classes registered in `plugin.xml` are found at runtime only, so new ones are added there.

## Review Focus

1. **A manager running outside the IDE.** Example: `claude --resume <manager id>` in a terminal. Opening the plan must show "running elsewhere" with Switch to Window / Open Anyway, not start a second process. Task 2 keeps the check and Task 6 calls it on every start; tested by hand in Task 8.
2. **`/clear` in the manager.** The store must move to the new id, or the next open resumes the old conversation. `PlanManagers.moveSession` is tested in Task 1 and wired in Task 4.
3. **A plan deleted while its tab is open.** The view becomes a notice and the manager process ends. `planViewOf` returns null, tested in Task 5.
4. **Typing in an inline field while the plan changes underneath.** The text survives the rebuild, and a save on a deleted item changes nothing. Task 6 keeps `PlanEdit` across rebuilds. `SessionFolders.editTask` on a missing id already returns the structure unchanged (existing behaviour).
5. **Two windows of this IDE opening the same plan.** One `PlanVirtualFile` instance per plan means each window has its own tab of the same file. The newest pane takes the process (split rule); the other shows Show Here. Task 3 registry, tested by hand in Task 8.

- **Splitter.** An `OnePixelSplitter(false, "dev.myair.planView.split", 0.55f)`. The left side is a `JBScrollPane(PlanPanel)`; the right is `pane.component`. The pane is `SessionPane(project, PlanFiles.startManager(...), checkFirst = true)`, a child disposable of the editor.

- **Adding.** `+ Add task` and `+ Add milestone` open a `NewTask` or `NewMilestone` edit. After a save, the same edit stays open, empty.
