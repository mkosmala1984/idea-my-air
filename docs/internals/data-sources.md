# Where the data comes from

Moved from CLAUDE.md. All state is read from files `claude` writes; the plugin never talks to a `claude` process. Unknown registry statuses and missing fields throw rather than being skipped, so a new `claude` release that changes these formats fails loudly.

- **Profiles** (`store/Profiles.kt`): a profile is a separate Claude Code config directory (`CLAUDE_CONFIG_DIR`) with its own `projects/` and `sessions/`, so skills, hooks, plugins and `CLAUDE.md` differ with the same account. `~/.my-air/profiles.json` (`ProfileStore`, version 1, `{name, dir}`; a blank, repeated or `default` name, a relative or repeated `dir`, one equal to `~/.claude`, a quote in a `dir` or an unknown key throws) lists them; `default` is `~/.claude`, implicit, never in the file. Every reader below runs per profile and is merged (`ProfileReaders`, `mergeSessions`, `mergeLive`, `service/ProfileReads.kt`): `ClaudeSession.profile` and `LiveSession.profile` are the directory the file lay in, one id in two profiles throws naming both directories, a profile lacking `projects/` or `sessions/` throws (`requireProfileDirs`), one watcher covers them all, each scanner has its own cache file (`default` keeps `scan-cache-<jar8>.json`, another adds a hash of its dir), and Claude Desktop sessions are read for `default` only. `ClaudeSessionsService` rebuilds the readers on the refresh thread when `ProfileStore.all()` changed; `profileHome(name)` gives a session's directory (throws for an unlisted name), which skill reads, `hasTranscript` and `restartArgs` use.
- **Transcripts** `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl` (and each profile's `projects/`) (`ClaudeSessionScanner`). The directory name encodes the cwd lossily, so the cwd comes from the first line carrying a `cwd` field. `claude --resume` from another folder (as after `EnterWorktree`) copies the transcript into that folder's project directory, so one session may lie in several files: the copy with the latest message, else the longest, counts. `/bg` continues a session under a new id and leaves the old transcript a `continued-in` line naming it (`continuedInSessionId`); the old session is left out while the new one is among the scanned (`ClaudeSession.continuedIn`). Title: the last `custom-title` line (`/rename`), else the brief's `title`, else the last `ai-title` line, else the first human prompt; a skill the human ran counts as `/name args` (a line opening with `<command-message>`), a built-in command such as `/model` does not. Date: the `timestamp` of the last `user`/`assistant` line or `system` `local_command` line, outside sidechains and `isMeta`; not the file's mtime, which a mere `--resume` bumps by appending `attachment`, `mode`, `last-prompt` and similar lines. Project: on every refresh a session whose cwd is in a linked worktree that `.git/worktrees/*/gitdir` of a directory sessions ran in lists gets that main checkout as `ClaudeSession.project` (`inProjects`), so the folder bound to the project holds it wherever the worktree lies; once git forgets a removed worktree, its sessions keep their own cwd. A session Claude Desktop runs gets the folder it was started in (`originCwd` of `%LOCALAPPDATA%/Claude-Data/*/claude-code-sessions/*/*/local_*.json`, keyed by `cliSessionId`, `DesktopSessionReader`), so a removed Desktop worktree keeps its sessions in the project too; such a session is marked "Desktop" in its row. Added directories: `additionalWorkingDirectories` of the last `attachment` line of type `environment` (`--add-dir`, Desktop's extra folders), shown under the session in the tree. Where it works now (`workDir`): that line's `workingDirectory`, which follows `cd` and `EnterWorktree` while `cwd` stays where it started; the branch it started on (`startBranch`): `gitBranch` of the line the cwd came from, `HEAD` (no branch, or no repository) read as none. Model and effort: `message.model` and the top-level `effort` of the last `assistant` line outside sidechains, skipping `claude`'s own error replies (model `<synthetic>`). Changed files: `Write`/`Edit`/`MultiEdit`/`NotebookEdit` `tool_use` items inside `"type":"assistant"` lines; `api-request-shape` lines also name those tools and must not count. Artifacts: the `toolUseResult` of an Artifact publish (`artifact_id`, `url`, `title`, `path`) outside sidechains, one per id, the latest publish naming it. Skills: `names` of the `attachment` lines of type `skill_listing`, the one with `isInitial` replacing the list, later ones adding to it. MCP servers: the `mcp__<server>__<tool>` names of `deferred_tools_delta` attachments, `addedNames` added and `removedNames` removed as servers connect and go; a server whose tools are only `authenticate`/`complete_authentication` waits for a sign-in and is left out. Background tasks: a `Bash`/`PowerShell` result with `backgroundTaskId` (named by the call's `description`, else its command's first line), a `Monitor` result's `taskId`, an `Agent`/`Workflow` result with status `async_launched` (`agentId` and `description`, `taskId` and `summary`); what it runs: a shell's or monitor's `command`, an agent's `prompt`, a workflow's `scriptPath` (each required); its start is that result's `timestamp`, its output file the `Output is being written to:` path of a shell's result text or an agent's `outputFile`. One ends with a `queue-operation` `enqueue` line whose `<task-notification>` carries its `<task-id>`, a `<status>` (`completed`/`failed`/`killed`/`stopped`, any other throws; a monitor's events carry none), a `<summary>` naming a command's exit code and usually `<output-file>`; an agent sent another message notifies again, and the latest end counts. An agent's model is its launch result's `resolvedModel`; an agent's or workflow's `<usage>` (after its `<result>`, whose text may hold anything) gives tokens and tool uses, a workflow's also `agent_count`/`agents_done`/`agents_error`. A monitor's notifications without a status each count as an event (its final one may carry the last); an event opening with `[Monitor expired` ends it as expired. Tasks also die with their process, which the transcript does not record. Transcripts are append-only, so a rescan reads only complete lines after the stored offset; that state is saved in `~/.my-air/scan-cache-<hash of the plugin jar's path>.json` (by the first scan, then at most once a minute and on exit; `Saved.forJar`), one per jar, so the installed plugin and a sandbox keep their own, and tagged with a hash of the jar's `dev/myair/claude/` classes, so a restart reads only what was appended meanwhile unless the transcript-reading code changed, which reads everything; `subagents/` one level deeper is not listed.
- **Live registry** `~/.claude/sessions/<pid>.json` (and each profile's `sessions/`) (`LiveSessionRegistry`), one per running `claude`: `sessionId`, `status` (`busy`/`shell`/`waiting`/`idle`; `shell` counts as working, as in claude's own list), `waitingFor`, `entrypoint`, `procStart`, `cwd`, `startedAt` (each required). A running session with no transcript yet (`claude` writes one with the first message) shows in the tree and the pinned list as "New session" in that `cwd`, dated by `startedAt` (`unscannedSessions`, `ClaudeSessionsService.listed`; given its project with the scanned ones by `inProjects`), so a session started from a folder shows there at once; `sessions`, and so MCP and Session Context, keep only the scanned ones. A file outlives a killed process, so an entry counts only if the pid's start time equals `procStart`, a Windows FILETIME. `/clear` and `/resume` keep the pid and rewrite `sessionId`, which is how tabs follow their session. A file without `statusUpdatedAt` belongs to a `claude` still starting and is skipped. `kind` is `interactive` or `bg` (a background job's worker, `claude --bg` or `/bg`, which needs a `jobId`: `LiveSession.job`); `daemon` and `daemon-worker` run no session and are skipped, as is a `spare` worker started ahead for the next job, and any other kind throws. `/bg` typed in a session parks its process: its file keeps the old `sessionId` and gains `parkedJobId`, so it is no entry but goes into `parkedBy` of the job's (dropped when that job has none); when a job's worker and another process run one session, the worker is the entry.
- **Tab store** `~/.my-air/` (`TabStore`), owned by this plugin: `ides/<pid>.json` lists each IDE's session tabs, `requests/<pid>/` receives "focus this session" requests, `pins.json` holds the sessions pinned by hand, the running ones removed from the list and the settled ones (`Pins`; the list above the tree adds every session with a live process, `pinnedSessions`). Settled sessions are hidden from the list and the tree until the toolbar's Show All Sessions is on (`Pins.shown`); settling unpins, pinning unsettles. View Options can also hide from the tree (not the list) sessions whose last message is 3, 7, 14 or 30 days old. The toolbar's This Work Tree (kept per project, `dev.myair.thisWorkTree`) narrows the tree (not the list) to the sessions whose `workDir` or `cwd` lies in the work tree of the window's project, compared by root (`inWorkTree`, over `ClaudeSessionsService.heads`, which reads every session's cwd, work dir and project on each refresh), disabled outside a repository; the narrowed tree keeps its own `TreeState` (`.workTree` after the mode). Search (and `my_air_sessions_find`'s `query`) matches each word in the title, the cwd, `startBranch` or the branch checked out in `workDir` (`ClaudeSession.matches`, `branchOf`). It also finds a session by what was said in it: every word, as a fragment of 3 or more characters ignoring case and accents but not `ł`, in one message of the human or the agent, from the conversation index `~/.my-air/search.db` (`search/SessionIndex`: SQLite FTS5 with the trigram tokenizer, from the sqlite-jdbc the plugin bundles (the IDE's own is a library module no plugin can depend on), filled after every refresh from the offset each transcript was read to, shared by every IDE; `ClaudeSessionsService.searchContent`, `indexGeneration`; the panel searches off the EDT and renders again when the answer lands, unless the toggle Search in Conversations beside the search field is off (application property `dev.myair.searchConversations`, default on), `my_air_sessions_find` adds `match`, the text around the hit; see `search/README.md`). The rows the user expanded are kept, one `TreeState` per mode (application properties `dev.myair.treeState.projects`/`.folders`, `TreeStates.kt`), across rebuilds and restarts; a search expands everything and leaves them as they were. The selection survives a rebuild, found again by its rows' ids (`rowKeys`/`pathsOf`, the user objects' `toString`), never moved to a sibling or parent of a row gone as TreeState's would, since the tree's menu actions read it when clicked. A removed running session returns once it has a newer message and no longer works; refresh prunes dismissals that are over. Writes go to a temp file and are moved into place.
