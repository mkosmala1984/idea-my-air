# Plan folders and plan view

Moved from CLAUDE.md.

- Plan folders (`folders/Plan.kt`, `structure.json` version 3, now 4, and 5 while a plan uses what it brought): a folder may name a working directory (`Folder.workdir`, set from its menu or MCP `set_workdir`, written only when set, so a build before it reads the file until one is), where sessions started from it or below run; it holds no sessions and any folder may share it. A folder binds several directories (`Folder.dirs`; version 2's `project` reads as one) and may carry a `Plan` (its name is the folder's) of milestones and tasks, each of the three with a Markdown `description` (for the plan it is the ideal state; written only when set, edited with Edit Description..., shown in the tree's tooltips and the Plan card through the platform's `convertMarkdownToHtml`) (`PlanStatus`: pending, in_progress, waiting for the user, blocked by someone else, done, canceled; `next`). Milestone and task ids (`M<n>`, `T<n>`) come from one counter, `SessionFolders.nextId`, unique across the file and never reused, so a brief's `plan_task` names a task alone; no plan folder lies in another. Where a session shows (`placeOf`): under the task its brief names while it exists (`taskOf`), else the folder the user filed it in, else `sessions` when the user dropped it there (`unfiled`, version 4: such a drop marks it, filing it anywhere unmarks it; MCP `assign` with a null path only takes it out of its folder), else the folder its brief names (`Brief.folder`, an id read from the tool's result `ok, folder <id> at '<path>'`, so a rename or move keeps it; ignored once deleted or in a plan folder), else its project's bound folder. `my_air_set_brief` creates a missing `folder` one level below an existing folder, never at the top level or in a plan folder (`briefFolder`, history source `brief`); the brief's `plan_task`, `title` and `folder` keep their value when a later call, or a Desktop `update_plan`, leaves them out; a plan folder's other sessions go to `no task`. A `Plan` besides its `description` (the ideal state) and milestones holds `constraints` (Markdown), `decisions` (`D<n>`: ISO date, text, optional session), `requirements` (`R<n>`: text, an `EvalKind` assert/code/questions/judge, the plan's task ids delivering it, evidence) and a `review` (`ReviewStatus` not_done/in_progress/done, a commit, a date, `B<n>` blockers with `resolved`), and `next`, the counter of the next `R`, `D` and `B`: those ids are per plan and never reused within it (`restore` keeps the higher counter per plan and prefix), while `M`/`T` stay global. A requirement's status is derived, never stored (`RequirementStatus`): unproven without evidence, not done with any `not done: ` item, else proven; evidence items are exactly `test <Class> › <name>`, `commit <7-40 lowercase hex>`, `checked: <text>` or `not done: <text>` (`requireEvidence` throws on anything else). `toJson` writes version 5 only while a plan holds any new field (`Plan.usesVersion5`), else 4, so a build before 5 reads the file until then; once a plan has handed out an R/D/B id its `next` keeps it at 5 even after the entries are deleted. `PlanChanges` applies an agent's change list to one plan, as `FolderChanges` does for folders (ops `set_description`, `add_milestone`, `add_task`, `set_constraints` (null clears), `add_decision`, `add_requirement`, `add_evidence`, `set_review` (the commit is kept when left out), `add_blocker`, `update` (fields per id prefix), `move`, `delete`; a requirement's `tasks` must be of that plan); `my_air_plan_get` returns the plans of a directory (`planFoldersOf`: the plan folder its bound folder is or lies in, else every plan folder inside its bound folder, so a project may have any number of plans; then every plan folder whose own `workdir` holds the directory, since a directory binds to one folder only), `my_air_plan_apply` changes one, named by its path. The tree (`MilestoneRow`, `PlanTaskRow`, `NoTask`) drags milestones and tasks within their plan and refuses a session onto a task; the menu edits plans (`FolderEditing`); Session Context shows a Plan card (`planContextOf`), whose path opens the plan tab. A folder bound to a main checkout with linked worktrees holds, after its subfolders, the group Worktrees (`WorktreesGroup`, `SessionTree.kt`): each of them (`WorktreeRow`: its folder's name, the branch checked out there in brackets, grey italic once its folder is gone), newest first by the creation time of its `.git/worktrees/<name>` admin directory (`gitWorktrees`, `LinkedWorktree`; git records no date; `gitdir` may be relative to the admin directory), every bound directory's merged into one group; under each, the sessions whose `workDir` or `cwd` lies in it (as text, as a bound folder tells, so another case is another directory), which also stay where `placeOf` puts them (the counts take each once). The panel reads them after the branches (`readBranches`, for every folder's bound directories), landing apart, so a worktree that cannot be read leaves the branches current. It is a view, as `recent`: nothing drops into it; a worktree row's menu offers New Claude Session in its folder, which keeps its branch (`nodeDir`), of its main checkout's project (`nodeProject`, as other worktree starts), Open in IDEA and Open in Terminal, not New Claude Session in Worktree...; a filter keeps a worktree only with a matching session. An installed My Air older than version 4 cannot read the file once this one writes it.
- Plan view (`planview/`): a plan folder opens in an editor tab, the plan on the left and its manager session's terminal on the right. Entry points: Open Plan in the tree's context menu (Folders mode, on a plan folder and on its milestone, task and `no task` rows), the path link of Session Context's Plan card, and opening the manager session from anywhere (`ClaudeSessionOpener.open` first sends a session that `managedPlanFolder` names, the store's entry while that folder still has a plan (`hasPlan`), to `PlanOpener`); `PlanOpener` focuses the tab of another IDE that shows the manager (`TabsSync.focusElsewhere`), else opens the plan's file in this window. The tab's file is `PlanVirtualFile` (a `LightVirtualFile`) under `PlanFileSystem` (`myair-plan://<folderId>`), so the platform saves it with the open tabs and resolves it on startup, never into Recent Files; its title is the plan's name (`PlanTabTitleProvider`, "Plan" once the folder is gone) and its icon the target icon (`PlanFileIconProvider`). `PlanFiles` (application service) holds one `PlanVirtualFile` per plan folder per IDE for its lifetime, so an open plan is focused rather than opened twice, and the manager's `ClaudeSessionVirtualFile`, which is never opened as a tab: `SessionTerminals` keys processes by file identity, so a reopened plan tab finds the same file and binds a detached process again. `startManager` (EDT) keeps that file while `SessionTerminals.runs` it, else builds it again from the plan's entry in `~/.my-air/plan-managers.json` (`PlanManagerStore`, shared by every IDE; folder id to `PlanManager(session, cwd, project, profile)`, `profile` written only when not `default`, unknown keys throw): no entry starts a new session (`--session-id`) in the plan folder's start directory (`startFolder`, else the IDE project's) and files it in the plan folder (`ChangeSource.AUTO`, so its history snapshot reads as the plugin's), where it shows under `no task`; an entry resumes its session (`--resume`, or `--session-id` while no transcript exists) in the directories stored with it, so the cwd stays as at the first start; the service moves the entry when `/clear` or `/resume` gives the process a new id (`moveSession`), and every start prunes entries of folders gone. A manager runs in its stored profile (`PlanManager.profile`; a new plan's from the composer's chip or the adopted session, Open Plan with none stored: `default`; `hasManagerTranscript` looks in it) and, being useless without My Air's tools, is refused in a profile whose `.claude.json` has no http MCP server of the url of the default profile's `idea` one (`managerToolsRefusal`, `managerProfileRefusal`, read off the EDT, the latest check landing: the tab shows the reason and the command with Try Again, or the failure to read either file, nothing starts or is stored and the manager's file is dropped). A manager's start passes `managed` to `sessionPlan` and `manager = true` to `planPrompt`: it works in that plan on no task, wherever it was moved and whatever task its brief names, and the plan's prompt (`planPrompt`) holds Ideal state and Constraints when set, Requirements (a manager gets all, a session on a task those it delivers), the task's and milestone's, and for a manager the section "Managing the plan" (change the plan with `my_air_plan_apply`, add and edit freely, delete or move only after the user agreed; record a decision with `add_decision` when the ideal state, constraints or requirements change, evidence with `add_evidence` as tasks close, the review with `set_review` and `add_blocker`). `PlanEditor` (`PlanEditorProvider`, hides the text editor) is an `OnePixelSplitter` (`dev.myair.planView.split`, 0.55) of `PlanPanel` in a scroll pane and a `SessionPane` (`SessionPaneHost`) that checks the directory and registry before a start whenever no process runs yet. It builds at once in `init` when the folders are read, else on the first service notification after; until then, or while `foldersError` is set, it shows "Loading..." or the error and waits. A plan gone (its folder deleted or its plan removed while open, or before a restored tab was first shown) leaves "This plan no longer exists." for good, closes the manager's process and drops the manager's file (`PlanFiles.forgetManager`), the tab's file kept; when the plan comes back (a history restore, Add Plan again), `PlanOpener` closes such a tab in its window before opening the plan, so it opens in a new editor rather than beside the dead one. Remove Plan and Delete on a folder first ask (`confirmed` with `Closing.REMOVE_PLAN`/`DELETE_FOLDER`) when a manager this IDE runs for a plan going would be interrupted (`SessionTerminals.wouldInterrupt`, as `interrupted` reads it); a history restore or an agent's change list ends it unasked, as does a plan gone in another IDE. The tab's title follows a rename: `PlanEditor` updates the file's presentation when the plan's name changes, and when the plan goes. `planViewOf` builds the model from `SessionFolders` (milestones with progress, tasks, and under each task the sessions whose brief names it, the manager left out); `PlanEditor` hands it to `PlanPanel` on every service change, and the panel rebuilds only when what it shows changed (the plan, the open edit, and per session its id, title, live status, unread mark and age), keeping an open edit's component so text, caret and focus survive a change the manager makes meanwhile. The panel, in the composer's look (`prompt/Composer.kt`'s `Rounded`, `Chip`, `CARD`, `BAR`, on the editor background; `PaneFont`), shows the plan's name with Hide done (application property `dev.myair.planView.hideClosed`: done and canceled tasks left out), Expand All and Collapse All (`Folding.all`, every section, milestone and task), under it the progress of all its tasks (done of not canceled, a bar of segments for done, in progress, waiting and blocked: `statusCounts`, and those three in words: `openWork`) followed by the summaries `R <proven>/<all>` (`requirementsSummary`, none without requirements) and the review's (`reviewSummary`: unresolved blockers, else its status); the description shows in the Ideal state card, not in the header. Then five grey cards, one per `Section` (`sectionCard`, `PlanSections.kt`), each with a chevron, its name, a summary and a `...` menu: Ideal state (the description; Edit Ideal State), Constraints (Edit Constraints), Decisions (count; newest first by date, then number, each with date and id; Add Decision, per item Edit and Delete), Requirements (`R <proven>/<all>`; a status glyph, id, text, an eval chip and its task ids, the evidence dim and read-only below; Add Requirement, per item Edit, Eval and Delete) and Code review (its status with commit and date, then the blockers with Resolve/Reopen, Edit and Delete; the menu sets its status and adds a blocker). A section without a text shows a `+ Add ...` link. Sections fold like milestones, by default Requirements open, Code review while it has an unresolved blocker, the others while empty. After them a grey card per milestone (chevron, id, title, the most urgent of its tasks' sessions and the newest age, progress and its bar of the same segments, a `...` menu with Rename, Mark Done/Reopen, Edit Description and Delete) listing its tasks. Milestones and tasks fold (`Folding`, in memory): by default a milestone is open unless done, a task open when in progress or waiting; a click on a milestone's head or a task's line or head flips it, and an open edit keeps its item open; a fold rebuilds only the milestone cards it changes (`rebuild`), as a whole rebuild lays every Markdown text out again and flickers, and the panel's buttons are `ActionButton`s drawn at once, not a toolbar, which adds its buttons on a later update and shifts the row. Texts are edited only from the menus, never by a click on them. Titles (`SelectableTitle`, a borderless read-only `JTextField`, one line where an editor pane would wrap, that passes the pointer's coming and going and a click selecting nothing to its row), next steps and descriptions (DSL text cells made focusable) can be selected and copied. A head is plain Swing (`head`), not a DSL row, so it is as high as its tallest part. A task's head is its status icon, a button that opens the statuses, id, title, the most urgent session's icon and the newest age (a folded one: else its next step) and a `...` menu of all its actions (`taskMenu`): Status (the statuses as toggles), New Session and New Session in Worktree... for that task as `NewSessionInDirAction` with a `PlanStart`, in the plan folder's start directory, Rename, Edit Next Step, Edit Description and Delete, the deletions being the tree's `deleteMilestone`/`deleteTask`. A folded task is that head alone, one line; an open one a white card: the head in the very place and size of the folded line, then (only when there is any) its next step, its Markdown description and session rows (status icon, bold title when unread, age; a click opens the session through `ClaudeSessionOpener`); then `+ Add task` / `+ Add milestone`. Markdown goes through `convertMarkdownToHtml` and `styledHtml` (`MarkdownHtml.kt`), which styles code, code blocks, quotes and headings inline (the DSL text cell reads a `<style>` only from its own head; headings in percent, so they follow the font size), colours read from the theme on each build and again on a theme change. Texts are edited in place (`PlanEdit`: `Title`, `Next`, `Description` of the plan, a milestone or a task, `Constraints`, `NewDecision`, `NewRequirement`, `NewBlocker`, `NewTask`, `NewMilestone`; `InlineEdits.kt`): Rename or Edit Next Step turns a title or next step into a field (Enter saves, Esc cancels) and Edit Description into an area with Save and Cancel (Ctrl+Enter saves), the shortcuts registered through the keymap so Esc does not reach the editor; `PlanEdit.apply` returns the change that `updateFolders` applies by id to the structure as it is then, so an item deleted meanwhile is left as it is; a blank title is refused and its field stays, an empty next step or description clears it, a new item's field stays open and empty for the next, and an edit whose item the manager deleted closes. A plan tab counts as its manager's tab wherever tabs are read: `sessionFileOf` (a session tab's file, a plan tab's manager file, none before it first starts nor while its folder holds no plan) replaces the open session files in `SessionHosts` (`findTab`, `openTabs`, so cross-IDE sync lists the manager's session id), and `shownSessionFiles` (it over the open tabs) in `retarget` (the manager's file follows its process's session and its presentation is updated on `tabFileOf`, the plan's file for a manager) and in `tabHeads`; `ActiveSession` takes the selected plan tab's manager as its session, so Session Context and Branch Diff follow it, and `PlanEditor` calls its `tabFileChanged` when the manager's file appears or goes; `findTab` returns `tabFileOf` of a detached manager, so focusing it reopens the plan tab. An agent replaces a plan's manager with the MCP tool `my_air_plan_set_manager` (`FoldersMcpToolset`), say to move it to another directory after starting a session there: `managerRefusal` refuses a session managing a plan already, unknown, a job's, running outside this IDE or still starting; else the session is filed in the plan folder and stored by `PlanFiles.adopt`, which returns the previous manager and detaches its process whatever `keepDetached` says (`SessionTerminals.detach`), as it may be the caller waiting for its answer, every open plan tab of the plan rebinds (`PlanEditor.showManager`), the plan opens in the calling project (`PlanOpener.openHere`), the session gets `planPrompt(manager = true)` as Turn into Plan sends it and its own tab closes; `my_air_plan_get` names each plan's `manager`; the result also gives the plan's `dirs` and `workdir` and, when the new manager's cwd lies in neither, a `hint` to set the plan's `workdir` to it with `my_air_folders_apply` (`managerSetJson`). A plan tab open in another IDE keeps the previous process until reopened. A session's menu (tree and pinned list) offers Turn into Plan... (`TurnIntoPlanAction`, `TurnIntoPlan.kt`), unless the session manages a plan or shows in one: a new plan folder, named in a dialog that starts with its title (`askFolderName`), in the folder it shows in (`placeOf`, else the top level), the session filed there and stored as its manager (`PlanFiles.adopt`); its process in this IDE becomes the manager's file, so the plan tab, opened next, binds that process (its pane takes it, the session tab's shows Show Here) and the session's tab then closes without ending it; with no process here the plan tab resumes it. Either way the session gets `turnIntoPlanMessage` as a message: a request to fill the new, empty plan from its conversation and report, followed by `planPrompt(manager = true)` (`SessionPane.send`: bracketed paste, then Enter; a text of several lines or over 400 characters goes into a file of `~/.my-air/messages` (`PromptFiles`) and the message names it (`messageToType`), as the terminal hands claude a long paste in pieces and claude takes only the first as the paste, the rest and the Enter as typed text; without a process, the first prompt after `--` of the manager's start, `PlanFiles.adopt`), since neither a running process nor a resumed one reads a new system prompt before it compacts.
